# API pública v1: endpoints de provisionamento (clients, hosting, git deploy)

Esta mudança abre a API pública v1 para escrita de provisionamento: cadastro de clientes finais (`ClientsController`, novo), criação/suspensão/parada de VPS (`HostingController`), e deploy via Git (`ApplicationsController`). O isolamento multi-tenant é centralizado em dois helpers novos no `BaseApiController` — `clienteIdsGerenciados()` (o próprio cliente da key + filhos em `clients.created_by_client_id`) e `resolverClienteAlvo()` (valida o `client_id` do body contra essa lista). Acompanham migrations para a coluna `created_by_client_id` e para liberar o status `deploying` em `git_deployments`, além de um novo job `parar_vps` e eventos de webhook. A modelagem de tenancy é consistente e os placeholders de SQL estão corretos; os problemas estão na borda do contrato (webhooks prometidos que nunca disparam) e em desvios de convenção.

Watch for: dois webhooks terminais (`hosting.ready` e `application.deployed` no deploy inicial) são prometidos nas respostas da API mas nunca disparados pelos workers — **confirmed**. O suspend da API grava `suspended_payment` no banco mas responde `suspended` — **confirmed**. Migration `0090` não é idempotente, divergindo da convenção `ADD COLUMN IF NOT EXISTS` do projeto — **confirmed**.

**Verdict**: NEEDS_CHANGES

## High-level view

O isolamento multi-tenant está correto nos caminhos de escrita. `resolverClienteAlvo()` barra `client_id` fora da árvore gerenciada antes de qualquer efeito, e `mudarEstado`/`showGitDeploy`/`redeployGitDeploy` filtram por `client_id IN (...)` montado só a partir de `clienteIdsGerenciados()`. `ClientsController` isola leitura e escrita por `id = self OR created_by_client_id = self`. Não há query de escrita que esqueça o filtro de tenant.

A verificação de escopo e o guard de sandbox estão presentes em todos os endpoints de escrita, sempre antes de qualquer efeito colateral. Vale uma observação de ordem: alguns métodos checam escopo e validam o corpo antes de `isSandbox()`, outros checam sandbox logo após a validação — o comportamento é correto em ambos, mas a ordem relativa entre `resolverClienteAlvo` e `isSandbox` difere entre `criar` e `criarGitDeploy`.

A construção de SQL com `IN (...)` usa placeholders posicionais `?` com `array_merge`, sem concatenação de valores. Não há injeção. O único risco teórico é `IN ()` vazio, que não ocorre porque `clienteIdsGerenciados()` sempre contém ao menos o próprio cliente nos caminhos autenticados.

O contrato de webhooks é o ponto fraco. As respostas de `POST /hosting` e `POST /applications/git` instruem o cliente a aguardar `hosting.ready` e `application.deployed` para saber que o provisionamento/deploy terminou, mas nenhum worker dispara esses eventos ao concluir — só `redeployGitDeploy` (re-deploy manual) emite `application.deployed`. O cliente fica esperando um evento que não chega.

Há inconsistências de estado entre a resposta da API e o que é persistido: suspend responde `suspended` mas o job grava `suspended_payment`, e reutiliza `suspenderPorPagamento` (semântica de inadimplência) para uma suspensão administrativa de revenda.

As migrations trazem um desvio de convenção: `0090` usa `ADD COLUMN` simples (não idempotente), enquanto o restante do histórico de `git_deployments`/`plans` usa `ADD COLUMN IF NOT EXISTS`. E `criarGitDeploy` grava `status = 'deploying'`, que só é aceito depois que `0091` roda — acoplamento de ordem entre código e migration.

### Isolamento multi-tenant: helper central e os caminhos de escrita

O desenho de tenancy é o acerto central da mudança. `clienteIdsGerenciados()` resolve a árvore `self + filhos(created_by_client_id)` uma vez, e `resolverClienteAlvo()` rejeita qualquer `client_id` fora dessa árvore com 403 antes de tocar o banco. `POST /hosting` e `POST /applications/git` passam por esse resolve e só então checam ownership da VPS contra o `clienteId` resolvido (`WHERE id = :id AND client_id = :cid`), então não há como provisionar sobre VPS de terceiros.

Os caminhos que operam sobre recursos existentes — `mudarEstado` (suspend/stop), `showGitDeploy`, `redeployGitDeploy` — filtram por `client_id IN (...)` construído exclusivamente a partir de `clienteIdsGerenciados()`:

```php
$ids = $this->clienteIdsGerenciados($req);
$placeholders = implode(',', array_fill(0, count($ids), '?'));
$stmt = $pdo->prepare("SELECT id, status, client_id FROM vps WHERE id = ? AND client_id IN ($placeholders) LIMIT 1");
$stmt->execute(array_merge([$vpsId], $ids));
```

`ClientsController` isola leitura e escrita por `(id = :self OR created_by_client_id = :self2)` tanto no `listar` quanto no `show`, e grava `created_by_client_id = self` na criação. Não encontrei query de escrita sem filtro de tenant.

Observação de borda: se `clienteIdsGerenciados()` retornasse `[]`, `array_fill(0, 0, '?')` produziria `IN ()`, um erro de sintaxe SQL. Isso não acontece nos caminhos autenticados (o helper sempre inclui `self` quando `clienteId` não é null, e as rotas estão sob `$apiAuth`), mas uma guarda explícita (`if ($ids === []) return $this->naoAutorizado();`) elimina um 500 silencioso caso o contrato de auth mude.

### Verificação de escopo e sandbox: presentes, com ordem relativa inconsistente

Todo endpoint de escrita checa `temEscopo(...write)` como primeira ação e retorna 403 antes de qualquer efeito. O guard de sandbox também está em todos os POSTs, retornando `respostaSandbox` antes de escrever. O que varia é a ordem relativa: `HostingController::criar` chama `isSandbox()` **antes** de `resolverClienteAlvo()`, enquanto a validação de ownership fica depois; `criarGitDeploy` segue o mesmo padrão. O efeito é que, em sandbox, um `client_id` inválido no body não é validado — a resposta simulada é retornada mesmo para um alvo que o chamador não gerencia. Como o sandbox não escreve nada, não há vazamento de dados; é só uma divergência de contrato (um `client_id` proibido devolve 201 simulado em vez de 403). Vale uniformizar se o sandbox pretende espelhar as validações de produção.

### Contrato de webhooks: eventos terminais prometidos mas não disparados

As respostas de criação instruem o integrador a aguardar um webhook para o estado final:

```php
// HostingController::criar
'note' => 'VPS provisioning started. Track status via GET /hosting/show?id=' . $vpsId
          . ' (provisioning → running) or the hosting.created / hosting.ready webhooks.',
```

`hosting.created` é disparado de forma síncrona na criação. Mas `hosting.ready` — o evento que sinaliza `running` — não é emitido por nenhum ponto do código; `provisionar_vps` chama `VpsProvisioningService::provisionar`, que faz `atualizarStatusVps($vpsId, 'running')` sem disparar webhook. O evento está na allow-list do `WebhookService` e documentado no changelog/i18n, mas é inerte.

O mesmo vale para o deploy Git. A nota promete `deploying → active` via `application.deployed`:

```php
'note' => 'Deploy queued. Track via GET /applications/git/show?id=' . $deployId
          . ' (deploying → active) or the application.installed / application.deployed webhooks.',
```

`application.installed` dispara na criação. Mas o worker `git_deploy` chama `GitDeployController::executarDeployPorId` e encerra sem emitir `application.deployed`. O único lugar que dispara esse evento é `redeployGitDeploy` (re-deploy manual acionado por outra chamada de API) — exatamente o caminho que o integrador não percorre no fluxo inicial. Resultado: quem seguir a documentação fica aguardando indefinidamente a confirmação de conclusão.

Isto é funcional, não cosmético: o valor do fluxo assíncrono (202 + webhook) depende do evento terminal existir. Ou os workers passam a emitir `hosting.ready`/`application.deployed` ao atingir o estado final, ou as notas e a allow-list devem parar de prometê-los.

### Suspend: estado reportado diverge do persistido e reusa caminho de pagamento

`mudarEstado('suspend')` enfileira `suspender_vps` apenas com `{vps_id}` e responde `status: 'suspended'`:

```php
$novoStatus = $acao === 'suspend' ? 'suspended' : 'stopping';
// ...
$pdo->prepare("INSERT INTO jobs (type, payload, ...) VALUES (:t, :payload, 'pending', NOW())")
    ->execute([':t' => $jobType, ':payload' => json_encode(['vps_id' => $vpsId])]);
```

O handler `suspender_vps`, com `assinatura_id` ausente, pula a checagem de assinatura e chama `VpsProvisioningService::suspenderPorPagamento`, que grava `atualizarStatusVps($vpsId, 'suspended_payment')`. Então o cliente que fizer `GET /hosting/show` logo depois verá `suspended_payment`, não o `suspended` que a resposta do POST anunciou. Dois problemas se somam: o status reportado não bate com o persistido, e a suspensão administrativa de revenda está reaproveitando o caminho semântico de inadimplência (`suspended_payment`, bloqueio de vhosts por pagamento). Para `stop` a resposta diz `stopping` e o job `parar_vps` grava `stopped` ao concluir — aceitável como transição assíncrona, mas `suspend` não tem um estado intermediário análogo.

### Migration 0090: desvio da convenção idempotente

O histórico recente de migrations do projeto adota `ADD COLUMN IF NOT EXISTS` (ver `0086_git_deploy_auto_deploy`, `0087_plans_is_custom`, `0056_git_deploy_auth_token`) ou o padrão `information_schema` + `PREPARE` (ver `0004_add_client_fields_for_billing`, `0047_client_subdomains`). A nova `0090` abandona ambos:

```sql
ALTER TABLE clients ADD COLUMN created_by_client_id INT UNSIGNED NULL DEFAULT NULL AFTER is_managed;
ALTER TABLE clients ADD COLUMN external_ref VARCHAR(120) NULL DEFAULT NULL AFTER created_by_client_id;
ALTER TABLE clients ADD COLUMN notes TEXT NULL AFTER external_ref;
ALTER TABLE clients ADD KEY idx_clients_created_by (created_by_client_id);
```

Se qualquer uma dessas colunas já existir (re-execução, ambiente parcialmente migrado), o `ALTER` aborta. O código de runtime tolera a ausência da coluna (`clienteIdsGerenciados` captura `\Throwable` e opera só com o próprio cliente), mas a migration em si não tolera presença. Alinhar à convenção `IF NOT EXISTS` fecha o buraco.

### Status `deploying`: acoplamento entre INSERT e migration 0091

`criarGitDeploy` grava `':st' => 'deploying'` em `git_deployments.status`. Antes de `0091`, a coluna é `ENUM('active','inactive','error')` — gravar `'deploying'` nela resulta em string vazia (MySQL não-estrito) ou erro (modo estrito). `0091` troca para `VARCHAR(20)`, resolvendo isso, e as duas migrations acompanham a mudança. É um acoplamento esperado, mas que exige que `0091` seja aplicada antes do primeiro `POST /applications/git` em produção; caso contrário o estado inicial do deploy fica corrompido silenciosamente. O `redeployGitDeploy` tem a mesma dependência (`UPDATE ... SET status = "deploying"`).

### Consistência com os helpers do BaseApiController

Os status codes batem com a semântica (201 em `ClientsController::criar`, 202 nos POSTs assíncronos, 409 em `CLIENT_ALREADY_EXISTS`/`VPS_NOT_RUNNING`, 422 em validação). Uma assimetria menor: `criarGitDeploy` e os POSTs 202 chamam `sucesso(..., 202)` direto porque o helper `criado()` fixa 201 e não cobre 202 — não há helper dedicado para o caso aceito-assíncrono, o que fragmenta o padrão de resposta de criação.

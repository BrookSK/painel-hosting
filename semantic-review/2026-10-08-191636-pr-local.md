# Public payment link: tokenized checkout without login

An admin generates a one-time link (`/pagar/{token}`) tied to a client + plan + currency + period, and the client pays without logging in — PIX/boleto/card via Asaas for BRL, Stripe Checkout for USD. The token is 32 random bytes (64 hex), stored only as a SHA-256 hash with a 6-char hint; identity, plan, currency and period are read exclusively from the link record, never from request input, which closes the obvious tampering vectors. The flow leans on the existing `AssinaturasService`/`StripeCheckoutService` and the gateway webhooks for final confirmation and provisioning. CSRF is disabled for the whole `/pagar/` prefix and the endpoints are IP rate-limited.

Watch for: the token travels in a GET URL and is interpolated raw into the subscription-status polling fetch, so it leaks through browser history, `Referer`, and server access logs (confirmed). The reuse guard against double-provisioning is a non-atomic read-then-write with a race window (confirmed), and the `paid` status is set by a client-driven polling endpoint that re-queries the gateway, so it is advisory, not a trust anchor (confirmed). `resolverPorToken` looks the token up by a direct hash equality in SQL (confirmed) — acceptable because the stored value is a hash of high-entropy input, but worth noting. The public screen exposes the client's full name and masked plan details to anyone holding the link (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The token design is sound: `random_bytes(32)` is cryptographically strong, only the SHA-256 hash is persisted, and lookups go through a parameterized query against a unique indexed hash column. Because the lookup compares a hash of a 256-bit secret, timing-based enumeration is not a practical threat here and no `hash_equals` dance is needed. The real exposure is the token's lifetime as a URL: it lands in access logs, browser history, and any `Referer` sent to Asaas/Stripe assets, and that is the most likely way this secret escapes.

Tampering resistance is the strong point of the controller. Every money-relevant value — `client_id`, `plan_id`, `periodo`, `currency`, addons — comes from the link row, and the gateway calls recompute the amount server-side from the plan. A request body cannot change who pays, what plan, or how much. The only field accepted from the payer is their own CPF/card/holder data, which is appropriate.

The weak point is lifecycle and state. `iniciar` guards against creating a second subscription by checking `subscription_id > 0` and status `pending`, but the check and the write are separate steps with no lock or unique constraint, so two near-simultaneous submits (two payment methods, double-click, retry) can each pass the guard and spin up two VPS rows + two Asaas subscriptions + two charges. The `paid` status is written by the public `status`/`cartao` endpoints based on a live gateway query; it is fine as a UI signal but must not be the thing that triggers provisioning — the webhooks remain the source of truth, and they are.

The API surface is four public routes plus one admin route. CSRF is turned off for the entire `/pagar/` prefix; for the token-authenticated POSTs this is defensible since there is no ambient session cookie to ride, but the blanket prefix match is broader than needed and the reasoning should be explicit.

Data exposure on the public page is modest but real: plan name and client name render for any link holder, and the status JSON reflects gateway payment state. No CPF or email is echoed back, which is the right call.

1. **Token leaks via GET URL** — the 64-hex secret is in the path for every view/status/card request, so it persists in access logs, browser history, and `Referer` headers to third-party asset hosts. Consider setting `Referrer-Policy: no-referrer` on these pages and scrubbing the token from access logging; longer term a short-lived session cookie set on first `mostrar` would keep the secret out of the status/card calls.
2. **Non-atomic reuse guard** — `iniciar` checks `subscription_id > 0` then calls `criarAssinaturaDoPlano` (which creates VPS + subscription + Asaas charge) without a lock or unique constraint, so concurrent submits can double-provision. Add a conditional `UPDATE ... WHERE id = ? AND subscription_id IS NULL AND status='pending'` claim before creating, or a unique constraint on `subscription_id`, and only proceed if the claim affected a row.
3. **`paid` is client-triggered** — `status` and `cartao` write `status='paid'` from a polling response the payer controls the timing of. It is advisory only; confirm provisioning is gated solely on the Asaas/Stripe webhooks and never on this flag, and document that invariant.
4. **CSRF disabled for whole `/pagar/` prefix** — defensible for token-authenticated POSTs with no session cookie, but the prefix is broader than the four known routes. Keep it, but note that any future authenticated route under `/pagar/` would silently lose CSRF protection.
5. **Client PII on public page** — `client_name` (and plan sizing) render for any link holder. Low severity since no CPF/email is shown, but consider trimming the displayed name if the link may be forwarded.
6. **`expired` lazily set, `paid` never swept** — expiry is only computed on resolve; a link whose charge is paid via webhook is marked `paid` only if someone hits the polling endpoint. Reconcile `payment_links.status` from the webhook path so state is correct without client polling.
7. **Addons never pass admin UI** — `gerarLinkPagamento` always sends `[]` for addons while the service and view carry addon plumbing. Harmless now, but dead parameters invite confusion; drop or wire them.

### Token strength, storage, and lookup

The token is `bin2hex(random_bytes(32))` — 256 bits of CSPRNG output — and only `hash('sha256', $token)` is persisted, in a unique-indexed `CHAR(64)` column, with a 6-char `token_hint` for admin-side identification. `resolverPorToken` rejects anything not exactly 64 hex chars before the query, then matches `WHERE pl.token_hash = :h`. There is no `hash_equals` constant-time comparison, but it does not matter here: the comparison runs inside the database against a hash of a 256-bit secret, so there is no byte-at-a-time timing oracle and enumeration is infeasible against the keyspace (`confirmed`).

The one structural secret-handling weakness is `confirmed`: the token lives in a GET URL across `mostrar`, `status`, and the polling loop. In `pagar.php` the status poller does `fetch('/pagar/'+token+'/status')` with the raw token, so it is in the DOM and in every XHR URL. Access logs will capture it, browser history retains it, and if the page loads any third-party resource the token can ride along in the `Referer`. For a bearer credential that authorizes payment, URL placement is the main leak path. Mitigations: emit `Referrer-Policy: no-referrer` on these responses, exclude the path from access-log capture, and consider exchanging the URL token for a short-lived cookie on first load so subsequent status/card POSTs do not carry it.

### Value and identity come from the link, not the request

In `iniciar`, `cartao`, and `status`, every money-relevant field is read from the resolved `$link` row: `client_id`, `plan_id`, `periodo`, `currency`, `addons_json`. The gateway calls (`criarAssinaturaDoPlano`, `criarCheckoutAssinaturaDoPlano`, `pagarComCartao`) recompute the amount server-side from the plan record and the Asaas `paymentId`; none accept a client-supplied price. The only inputs taken from the payer are their own CPF/CNPJ, card data, and holder address. An attacker holding a valid token cannot swap the plan, change the amount, or redirect the payment to a different `client_id` via the body. IDOR via request tampering is `confirmed` closed — this is the strongest part of the change.

### Double-provisioning race

```php
if ($link === null || (string) ($link['status'] ?? '') !== 'pending') { ... }
if ((int) ($link['subscription_id'] ?? 0) > 0) { return redirect('/pagar/'.$token); }
// ... no lock here ...
$resultado = (new AssinaturasService(...))->criarAssinaturaDoPlano(...); // creates VPS + sub + Asaas charge
$service->vincularAssinatura($linkId, $subId);
```

The guard reads `status` and `subscription_id` from a snapshot taken by `resolverPorToken`, then creates the subscription and only afterward writes `subscription_id` back via `vincularAssinatura`. Between the read and the write there is no row lock, no `SELECT ... FOR UPDATE`, and no unique constraint on `subscription_id`. Two requests that arrive close together — the "iniciar duas vezes com métodos diferentes" case from the review brief, a double-click, or a client retry — can both observe `subscription_id = 0` and both call `criarAssinaturaDoPlano`, which (confirmed from `AssinaturasService`) inserts a VPS row, a `subscriptions` row, and a live Asaas subscription/charge each time. The result is duplicate provisioning and duplicate billing. This is `confirmed`.

The fix is to claim the link atomically before doing any gateway work: `UPDATE payment_links SET status='processing' WHERE id=:id AND status='pending' AND subscription_id IS NULL`, check the affected row count, and bail if it is zero. A unique index on `subscription_id` would also prevent the second `vincularAssinatura` from succeeding, though it would not undo the duplicate Asaas charge, so the pre-claim is the stronger fix.

### `paid` is a client-driven signal, not proof of payment

`status` (GET, polled every 5s by the page) and `cartao` both call `marcarPago` when the gateway reports `CONFIRMED`/`RECEIVED` or the subscription is `ACTIVE`:

```php
$pago = in_array($paymentStatus, ['CONFIRMED', 'RECEIVED'], true) || $subStatus === 'ACTIVE';
if ($pago) { $service->marcarPago((int) $link['id']); }
```

The flag is derived from a fresh server-side query to Asaas, so a payer cannot forge `paid` by crafting a response — they do not control what Asaas returns. What they do control is whether and when the endpoint runs, which means `payment_links.status` only advances to `paid` if someone actually polls. This is `confirmed`: the flag is a convenience/UI marker, not an authorization fact. That is fine as long as provisioning and entitlement are driven by the webhooks (`/webhooks/asaas`, `/webhooks/stripe`), which they are. The risk is if any future code trusts `payment_links.status = 'paid'` to grant access — it should not. Reconciling the link status from the webhook handler would also fix the "paid link never updated because nobody polled" gap.

### CSRF exemption

`Roteador::csrfObrigatorio` returns `false` for any path under `/pagar/`, joining `/webhooks/`, `/api/metrics/`, `/api/worker/`, and `/api/v1/`. For the public POSTs (`iniciar`, `cartao`) this is defensible: there is no session cookie in this flow, so a forged cross-site POST cannot ride ambient credentials, and the token in the URL is itself the capability. An attacker who already has the token can craft a POST regardless of CSRF, so CSRF tokens would add little. The caveat is scope: the exemption matches the whole prefix, so any route added under `/pagar/` later inherits the exemption silently. Keeping the exemption is reasonable; the prefix breadth is a `possible` future footgun worth a comment pinning it to the known routes.

### Public page data exposure

`pagar.php` renders `client_name` and plan name/price for anyone who opens the link, and `resolverPorToken` also selects `client_email` and `cpf_cnpj` into the row. The email and document are *fetched* but not rendered on the page, and the `status` JSON returns only `pago`, `sub_status`, `payment_status`, and PIX QR data — no PII. So the actual leak to a link holder is the client's display name and plan sizing (`confirmed`). Severity is low because a payment link is expected to be sent to the client themselves, but if links can be forwarded, the name disclosure is worth trimming. The brief's specific worry — CPF/email leaking on screen or via the status endpoint — does not occur in the current code.

### Rate limits

The limits are per-IP: view 60/min, iniciar 15/min, status 120/min, card 10/min. For a payment flow these are reasonable — the status poller runs every 5s (≈12/min) so 120/min leaves headroom, and 10 card attempts/min is a sane brute-force ceiling against the gateway. Since there is no session, IP is the only available key; behind a shared NAT or CDN this can over- or under-count, but that is inherent to anonymous endpoints and not specific to this change.

### Minor correctness notes

`gerarLinkPagamento` always passes `[]` for addons even though the service, migration (`addons_json`), and view all carry addon plumbing — the admin form has no addon selector, so the parameter is dead (`confirmed`, low severity). The `periodo` normalization differs slightly between layers: the service clamps to `{1,6,12}` while the admin form only offers `1` and `12` — harmless but a `possible` source of confusion if a 6-month option is added later. Expiry is only materialized on resolve (`strtotime(expires_at) < time()` flips `pending` to `expired`), so an unopened expired link stays `pending` in the table until someone hits it — acceptable for display logic but means `status` queries over the table are not authoritative without the lazy check.
